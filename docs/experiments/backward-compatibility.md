# Experiment — does what worked still work

Written before the measurement.

## The research question

**Does** ditto at `exp/test-invocation` reach the same verdict, mutant by mutant,
as ditto at `dfd8ed4`, on the path that existed in both — over the mutants of a
fixture carrying every virus family, measured on scratch modules in August 2026?

| Element | This question's |
| --- | --- |
| Interrogative phrase | does every verdict still hold |
| Variable, the counters that move | mutants generated, and labels whose column changes between the two revisions |
| Population, unit of analysis | the mutants of one scratch package, generated by the default virus set |
| Space and time | `dfd8ed4` against `exp/test-invocation`, Go 1.25, August 2026 |

The branch added a gated path, and a verdict changed during an integration
validation of it. That validation is what started this whole line of work. What
it never established is the thing this note asks: whether the path that already
existed still answers what it used to.

`Gated()` does not exist at `dfd8ed4`, so the comparison runs the **ordinary
path on both sides**. That is precisely the surface backward compatibility is
about.

The golden cannot answer it. `testdata/golden/release.txt` was created **on this
branch** — 118 insertions and no deletions — so it pins what the changed code
does and has never seen the code before it. It is a guard going forward.

**FINER** — *Feasible*: two scratch modules, one per revision, minutes.
*Interesting*: this is the goal, not a step towards it. *Novel*: no before/after
comparison exists; every measurement so far compared two paths of the same
revision. *Ethical*: `dfd8ed4` is materialised with `git archive` into a
throwaway directory; no checkout is touched. *Relevant*: whether this branch can
be merged at all.

**PICOT** — **P** the mutants of the scratch package · **I** the branch ·
**C** the same fixture against `dfd8ed4` · **O** mutants generated, and labels
that change column, both exact integers · **T** one release per revision.

## The hypotheses

**H1 — the population is unchanged.** The branch touched `internal/ditto`, which
now keeps a file's mutants together, and `internal/gomutatedfile`. Either could
change how many mutants exist or what they are called.

*Prediction: both revisions generate the same number of mutants, with the same
labels. Falsified by one mutant more, one fewer, or one named differently* —
and if it fails, H2 has nothing to compare and says so rather than reporting a
difference that is really a renaming.

**H2 — every verdict is unchanged.** Each mutant is reported in the same column
by both revisions.

*Prediction: zero labels change column. Falsified by one.*

**H3 — if a verdict moved, it moved from wrong to right.** The one movement seen
so far was the ordinary path scoring a mutant that never ran, and the branch
scoring it honestly.

*Prediction: every moved label is one whose mutation fails to compile on its
own, so the old verdict was a kill no test earned. Falsified by one that
compiles* — which would be a verdict this branch broke rather than repaired.

**What would refute all three:** a difference in the report that is neither a
population change nor a verdict change — ordering, formatting, a label's shape.
That is still a backward-compatibility break for anyone diffing output, and it
belongs to a question about the report rather than about verdicts.

## Decision rule, fixed in advance

- H1 and H2 hold → the ordinary path is intact and the branch is compatible on
  verdicts.
- H2 fails and H3 holds → the only changes are repairs; each one is named in the
  note and in `backlog.md`, and the branch is compatible in the sense that
  matters.
- H3 fails → the branch broke a verdict. It does not merge until that is
  understood.
- H1 fails → the comparison is void until the population is reconciled.

## Controls

1. **The comparison can disagree.** Established in
   `instrumentation-fidelity.md`, and the same extraction code is used here: one
   added test moved survivors from 14 to 11.
2. **Both revisions are really the revisions.** Each scratch module's `replace`
   is checked to point at a tree whose `git` provenance is recorded, and the base
   tree must not contain `Gated`, which the branch introduced.
3. **The fixture is green before anything is mutated**, so no verdict on either
   side is inherited from a red baseline.

## Fixture

Two scratch modules in `t.TempDir()`, identical but for the `replace` target:
one pointing at the worktree, one at `dfd8ed4` materialised with `git archive`.
The fixture package carries comparisons, integer literals in and out of index
position, a switch over literal cases, string concatenation, a loop with a
break, and a local read only inside an `&&`.

## Results

### Controls

1. **The comparison can disagree**, with the same extraction code that moved
   survivors from 14 to 11 in `instrumentation-fidelity.md` when a test was
   added.
2. **Each run proves which revision produced it.** The base copy's banner is
   stamped `Releasing DITTO-AT-BASE…` before it is built, and the run that claims
   to be the base must carry it while the run that claims to be HEAD must not.
   The base tree is also checked to have no `func Gated`, which the branch
   introduced.

   The control was then broken on purpose — the "before" run pointed at the
   worktree — and it fired: *the run that claims to be dfd8ed4 does not carry its
   marker, so it is not the base and nothing below is a comparison.* Without
   that, two revisions that silently turn out to be the same one agree about
   everything, which looks exactly like backward compatibility.
3. **The fixture is green before anything is mutated.**

### H1 holds — the population is unchanged

    dfd8ed4 : total 31
    HEAD    : total 31

Same count, same labels. `internal/ditto` keeping a file's mutants together
changed no mutant's existence or name.

### H2 holds — no verdict moved

    dfd8ed4 : total 31, killed 7, survived 24
    HEAD    : total 31, killed 7, survived 24

Compared by label, not by size: the symmetric difference of the two survivor
sets is empty. Nothing that was killed survives, and nothing that survived is
killed.

### H3 is not decidable here

No label moved, so the claim that every movement is a repair has nothing to range
over. Recorded as undecidable rather than held: a hypothesis satisfied by having
nothing to test is not corroborated.

### Verdicts: 2 of 3, the third undecidable

### The same comparison on the repository the defect was found in

A scratch fixture is convenient and therefore suspect. The verdict that started
this line of work was seen on dharness's `internal/setup/writer.go`, so the
comparison was run there too: a copy of the repository, the release scoped to
that one file the way the wrapper scopes it, both revisions.

    dfd8ed4 : total 35, killed 33, survived 2
    HEAD    : total 35, killed 33, survived 2

Identical, and 35 is the count a real release reported for that file, which is a
second thing this run had to agree with and did.

**So the kill that was said to be spoiled was never a regression.** It moved
between the ordinary path and the *gated* path of the same revision, not between
revisions — and `disagreement-class.md` measured that the gated path is the one
that is right. The branch changed no verdict the ordinary path used to give.

## What this does NOT establish

- **The path that was not compared.** `Gated()` does not exist at the base, so
  nothing here says the gated path agrees with anything. That is
  `disagreement-class.md`, where it deliberately does not — and is right.
- **Two fixtures, not a repository swept whole.** 31 mutants of a scratch
  package and 35 of one real file. `false-kills.md` counted 1293 over dharness's
  `internal/`; nothing here compared those.
- **The false kills are on both sides.** Two of `writer.go`'s mutants do not
  build, and both revisions score them killed. The branch did not introduce that
  and does not fix it on the ordinary path — which is the point of `backlog.md`
  entry 6, and is not what this note asks.
- **Verdicts, not bytes.** Two runs can report the same columns while printing
  them in a different order. Anyone diffing ditto's output rather than reading
  its verdicts is not covered by this.

## How to run it again

    DITTO_PROBE=1 go test . -run TestBackwardCompatibility -v

    DITTO_PROBE=1 DITTO_COMPAT_REPO=<a repository> \
      go test . -run TestBackwardCompatibilityOnTheRepository -v

The repository is copied, never mutated in place, and the base revision is
materialised with `git archive` rather than a linked worktree.
